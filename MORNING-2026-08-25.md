### #536 — T10, the launch blocker

Kevin: *"the Standings & Leaderboard and Results tab is correct in the Survivor
pools, but not in any of the other NFL pools."*

Survivor showed ONE Standings tab; Pick'em and Margin showed two with
overlapping names, and the season table's dominant columns were week-scoped —
so a season page read as a weekly page and members went to Results looking for
season totals.

Now: one **Standings & Results** tab with a scope control — **Season** (default)
· **{Week label}** · **Summary**. The two tables are the same tested components
re-parented; no ranking logic moved. Results left the tab strip, but `results`
stays a valid `?tab=` value and is normalized to the week segment, so stale
shared links land instead of falling back to the dashboard. Survivor is
unchanged. Help's `pool.nfl.results` page merged into `pool.nfl.standings`.

**Three deviations from the signed plan, all named in the PR:** Summary is
offered to Pick'em too (the plan's literal "Margin only" would have deleted the
Pick'em season grid, which nothing else replaces); the week segment is labelled
with the week label rather than "This Week" (the selector is pool-wide, so "this
week" is a lie when browsing Week 1 in Week 5); and Margin's old "Margin
Standings" sub-view is gone, which the plan itself named as part of the problem.

**Known, for your call:** the Pick'em **Season** segment is now three columns —
Rank / Player / Total Points. Honest, because everything else on that table was
week-scoped, but sparse. A "Weeks scored" or "Weeks won" column is a small
follow-up; inventing a column is not re-parenting, so it was not done in a
launch-blocker PR.

### #537 — feed placement + pinned message

Kevin: *"move the Pool Feed card next to the Pool Standings card… The bottom of
the page is useless. I also want the Pool manager to be able to PIN a message to
the top of the Pool home page, right below the score ticker."*

The feed card moved into the bento grid immediately after Pool Standings. On a

and Margin already fill that row, so there the card spans both columns rather
than opening a new gap. Still one `BanterFeed` component and one subscription,
so the member view and the commissioner card cannot drift.

**The pin is stored as `pool.pinnedMessageId`, not a flag on the message.** You
asked for the reasoning, so: `pools/{id}/messages` keeps `allow update: if
false` — a post can be removed but never silently rewritten under its author's
name — and "exactly one pinned at a time" becomes a property of the data rather
than a rule anyone has to enforce. **No `firestore.rules` change was needed.**

It is written through the `updatePoolSettings` **callable**, not `updateDoc`:
the pool document's client update rule ends with `poolIsEditable()`, which
permits a manager write only while the pool is DRAFT or OPEN — a direct write
would be denied mid-season, which is exactly when a pin is wanted. A new
`announcement` editability group is editable in every lifecycle phase.

Codex found a real one: `pinnedMessageId` becomes a Firestore **path segment**,
and `doc()` throws *synchronously* — inside the effect every member of the pool
runs. One bad value from one authorized commissioner would have taken the pool
home page down for everybody in it. Validated at both ends now.

### #538 — C1, super-admin per-pool feature toggle

Kevin: *"I, as the super-admin must be able to turn the feature on for any pool
at any time through a toggle switch or something."*

`adminUpdatePoolBilling({action:'override'})` could already do this — it merges
an arbitrary billing object — but there was no UI, and an audit row reading
`POOL_BILLING_OVERRIDE` says nothing about which feature moved.

New narrow callable `adminSetPoolFeature({poolId, feature, enabled})`:
`z.enum(ADDON_KEYS)` + a boolean, strict, SUPER_ADMIN, correlated, and audited as
`POOL_FEATURE_GRANT` / `POOL_FEATURE_REVOKE`. It writes the entitlement **and**
the paid ceiling (`billing.paid.addons`) — but the ceiling only when
`billing.paid` already exists, so a grant on a free or trial pool does not invent
a purchase record. It claims **no money moved**: no status, tier, `pricePaid` or
ledger write.

UI: a **Features** button on each row of the Super-Admin **All Pools** tab,
expanding one switch per add-on key, with explain-then-confirm. The AI copy names
the real Gemini spend.

It also fixed a defect in an existing guard:
`tests/callable-correlation-coverage.test.ts` blanked multi-line block comments
to a run of spaces, **eating the newlines** and shifting every line below them
up — so its lookahead window could credit one callable with its neighbour's
correlation id. Measured on this very diff.

### #539 — C2, mid-season add-on purchase

Kevin: *"a pool manager must be able to buy a premium feature anytime during the
season… purchase this feature and then have that feature automatically turned on
without my intervention."*

**Three blockers, one of which was not in the brief:**

2. 🛑 `finalizePoolPayment` treated **any** session arriving for an active pool

   A mid-season payment would have **taken the money and granted nothing**.
3. `featuresUnlocked` and `paid.addons` were written by **REPLACEMENT** — you
   asked me to confirm this, and yes: a second purchase revoked everything
   bought before it. **That also bit the hosting path**, because C1 can grant a
   feature on a free or trial pool and activation would have revoked your grant.
   Both paths now merge.

`purchaseKind: 'pool' | 'addon'` (defaulting to `'pool'`, so no existing client
changes). The add-on quote charges no base price, drops already-owned add-ons
before pricing — reading ownership from **both** `paid.addons` and
`featuresUnlocked`, so a commissioner cannot be sold something you already gave
them — carries the existing tier through, and refuses credits and coupons with a
message rather than ignoring them. Idempotency for add-ons comes from the ledger
row (id = Stripe session id), because `pricePaid` is an increment.

Buy button on the commissioner's AI card, and on the Bracket dashboard. No price
is rendered client-side (ADR-0001); Stripe's page shows it.

## 2. 🛑 OPEN DECISIONS — these need Kevin

### D-1 (from the brief) — branding customization is too weak

Your words: *"we need to make the customization better. It really does not do
anything noticeable to anyone… If this is a large lift or conflicts with the
light/dark functionality, come up with a way to make customization worth the
effort or tell me to kill it. I want the logo customization kept either way."*

**Measured.** `src/utils/brandingStyles.ts` (shipped in #526) drives four things
from `primaryColor`: a **6% rgba page tint**, a header-card border, a soft glow,
and primary action buttons. `secondaryColor` drives the active-tab underline. On
the dark navy theme a 6% tint is very nearly invisible. You are right.

**The tension.** The app is theme-aware: `--page`, `--card`, `--surface`,
`--line`, `--text`, `--muted`, `--faint` are CSS custom properties on `:root` and
`.dark`, and every surface token was chosen *against* `--page`. A
commissioner-chosen full-bleed background fights all of them at once.

| option | what it does | cost | contrast risk |
|---|---|---|---|
| **(i) Full page background = primaryColor** | replaces `--page` per pool and derives a readable text/surface ramp from the pick (luminance maths; `readableTextOn` already exists) | **High.** Every card, line and muted token has to be re-derived per pool, and the pool page is only part of the app — the shared header and nav still use the global tokens | **High.** A pale pick in dark mode gives white cards on a pale page with text tuned for navy; a dark pick in light mode inverts the problem. Roughly half of all picks land somewhere bad, and it fails *silently* |
| **(ii) Strong branded HEADER BAND** ⭐ | a full-width band behind the pool header, painted `primaryColor`, with `readableTextOn(primary)` text — the logo already sits there — plus the accent tabs and buttons that already work | **Low.** ~40 lines: one new `headerBand` style in `brandingStyles.ts` and one wrapper in the pool header. Tests are the same shape as T1's | **Low.** The band paints **both** its own background and its own text colour, so it never depends on `--page` and cannot fight light/dark |
| **(iii) Keep the logo, delete the colour pickers** | branding = logo only | Negative (deletion) | None |

**RECOMMENDATION: (ii).** It is the first thing anyone sees, it is where the
logo already is, it is theme-safe by construction because it owns both of its own
colours, and it is a small enough lift to ship and verify in one PR. I would also
raise the page tint from 6% so it is at least perceptible, but the band is what
does the work.

**On "approve as recommended" I build:** a full-width `primaryColor` header band
behind the pool name and logo, with automatically readable text; the existing
accent tabs and buttons kept; the page tint raised; **logo customization kept**;
one PR, with tests, NFL pool pages first (matching D4's weekend scope).

**(i) is the one to reject** unless you want the bigger project: it is the only
option whose failure mode is a member who cannot read the page, and it fails
without anyone noticing until they complain.
