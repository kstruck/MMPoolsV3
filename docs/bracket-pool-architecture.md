# Bracket Pools: Technical & Product Guide

This document outlines the architecture, rules, and edge cases for Bracket Pools within the March Melee platform. It serves as a reference for developers to understand the core functionality, configurations, and scoring engines.

---

## 1. Supported Tournament Types

The platform supports different structures depending on the number of rounds. The `BracketBuilder` and `scoring logic` dynamically adapt to these layouts:

- **NCAA Men's March Madness:** 6 Rounds (64 teams + 4 play-in games), structured into 4 standard regions and a Final Four.
- **Big East Tournament:** 4 Rounds (11 teams). Features byes for top seeds.
- **Big 12 Tournament:** 5 Rounds (14 teams). Features double byes for top seeds.

**Key Difference Map:**

| Tournament | Teams | Rounds | Base Structure |
| ---------- | ----- | ------ | ---------------- |
| NCAA | 68 (64 main) | 6 | `RegionBracket` + `FinalFourBracket` |
| Big East | 11 | 4 | `ConferenceBracketBuilder` |
| Big 12 | 14 | 5 | `ConferenceBracketBuilder` |

> *Developer Note:* The `round` index (1-indexed) is crucial. A Big East final is Round 4; NCAA final is Round 6. Never hardcode loops to `6` — always dynamically derive `maxRound` from tournament game data.

## 2. Admin Settings & Pool Configuration

Pool creators (Admins) configure pools via the `BracketWizard`. Key configurations include:

### 2.1 Access & Restrictions

- **Max Entries Per User:** Enforces how many unique brackets a single user can submit.
- **Max Entries Total:** Hard cap on the pool size.
- **Access Control:** Passwords, Waitlists, required Email/Phone details from entrants.
- **Entry Fee:** Integrated with payment instruction fields (e.g. Venmo handle). Note that platform payments are manual via peer-to-peer apps, not processed via Stripe.

### 2.2 Payout Structures

Admins define percentage splits for the top X places.

- Example: 1st (60%), 2nd (30%), 3rd (10%).
- Bonus options (e.g., "Best 1st Round", "Last Place Money Back").

### 2.3 Upset Bonus Settings

Admins can enable **Upset Bonuses**. If enabled, whenever a lower-seeded team (e.g., #12) defeats a higher-seeded team (e.g., #5), bonus points are injected based on the multiplier:
`Bonus Points = (Lower Seed - Higher Seed) * Multiplier`
*(Example: 12-seed beats 5-seed. Multiplier is 2. Bonus = (12 - 5) * 2 = 14 points).*

## 3. Scoring Engine Logic

The scoring engine lives primarily in `src/components/BracketPoolDashboard/bracketScoring.ts` and `src/utils/bracketScoring.ts`.

### 3.1 Base Scoring Systems

Defined point multipliers per round. Round index maps to index in an array:

| System | Array Definition | Notes |
| ------ | ---------------- | ----- |
| **CLASSIC** | `[10, 20, 40, 80, 160, 320]` | Standard doubling per round. |
| **ESPN** | `[10, 20, 40, 80, 160, 320]` | Mirrors classic logic on ESPNs default setting. |
| **FIBONACCI** | `[10, 20, 30, 50, 80, 130]` | Scaled progression to diminish the weight of later rounds. |
| **CUSTOM** | *User Defined Array* | e.g. `[5, 10, 20, 40]`. Admins specify points per round precisely. Must support arrays of length 4, 5, or 6 based on the tournament format. |

### 3.2 Maximum Possible Score calculation

For the dashboard "Current Standings", we need to compute `maxPossibleScore`:

- If a game is **FINAL**, the user earns points if their pick was correct, `0` if wrong.
- If a game is **SCHEDULED/IN PROGRESS**, the user earns *potential* points, **BUT ONLY IF** the team they picked is still `"alive"` in the tournament.
- `isTeamAlive(teamId)` specifically iterates across all FINAL games. If a team lost a concluded game, they are eliminated and can no longer generate potential points in future assumed rounds.

---

## 4. Tiebreaker Logic

When two users have identical scores, the engine defers to the `tieBreakerPrediction` input. This input represents a guess at the total combined points scored by both teams in the Championship Game.

There are two behaviors an Admin selects upon creation:

1. **Closest Absolute (Default):** Rank determined by `Math.abs(Prediction - ActualScore)`. The closest number wins, whether it was an over-guess or under-guess.
2. **Closest Under (Price is Right):** The highest guess *without going over* wins. If *all* tied entries went over the actual score, the engine defaults back to "Closest Absolute" logic as a fallback to break the tie cleanly.

---

## 5. Standings Computation

Standings are dynamically generated by evaluating the array of `BracketEntry` records against the current `Tournament` result snapshot.

1. Generate `ScoringResult` object for each entry: `{ score, maxPossibleScore, correctPicks, roundBreakdown, upsetBonusPoints }`.
2. Array sorted primarily descending by `score`.
3. If tie exists, sorted ascending by tiebreaker difference (Absolute or Under logic).
4. Rank number assigned sequentially. Note: true ties (exact same score, exact same tiebreaker delta) maintain identical ranks (e.g. 1, 2, 2, 4) if strict ranking is enforced.

---

## 6. Notable Edge Cases

1. **Incomplete / Null Picks:** If a user submits a bracket with "ghost" picks (null/empty string IDs), those specific slots yield `0` points safely. No breakage.
2. **Conference Tournament Custom Rounds:** An admin applying "Custom Scoring" to the Big East tournament will submit an array of `[x, y, z, q]`. The engine dynamically sets `maxRound = 4` and ignores missing index checks for assumed Rounds 5/6.
3. **Double Byes (Big 12):** Tournament bracket mappers explicitly wire the "slots". E.g., a Top-4 seed might auto-fill into Round 2 slots without producing a Round 1 matchup. Scoring correctly evaluates the existing slot, bypassing the absent play-in game.
4. **Seed Parsing:** `extractSeedFromTeamId(teamId)` must handle variable conference and region prefixes (e.g., `E1-Duke`, `MW16-UtahState`, `S10-UNC`). Handles regex matches specifically looking for `...[0-9]+-...` substrings inside bracket slot data.
