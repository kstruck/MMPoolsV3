# ADR 0003: A dedicated Member Record as the cross-type Roster + payment truth

Date: 2026-07-07 (revised same day after adversarial review)
Status: Accepted

## Context

"Who is a Member of this Pool, and have they paid?" has no single answer today. Membership and payment are recorded differently per Pool type, and the playable record is created only when a Member acts, not when they join.

Observed in code:

- NFL types (`NFL_PICKEM`/`NFL_SURVIVOR`/`NFL_MARGIN`): membership lives in `pools/{id}.participantIds[]` (+ a `users/{uid}/participations/{id}` mirror). An Entry at `pools/{id}/entries/{uid}` is written **only** by `submitNFLPicks`, carrying `paidStatus`. `joinNFLPool` writes no Entry and early-returns if the uid is already in `participantIds` (`nflPools.ts:168`).
- Bracket: **multiple Entries per Member** are allowed (`maxEntriesPerUser`), with random entry IDs (`bracketEntries.ts:60,82`). Bracket also uses `users/{uid}/joinedPools`, not `participations` (`bracketPools.ts:281`).
- Playoff: Entries keyed `uid_timestamp`, also capped per user; stored on `pool.entries` (`playoffPools.ts:174,196,108`). Note `statsTrigger.ts:18` already reads a **nonexistent** `playoff_entries` subcollection — an existing bug.
- Squares: `pools/{id}/participants/{uid}` index docs plus guest square claims; `"guest"` is pushed into `participantIds` (`squares.ts:111`) and guest claims only rewrite the `squares` array (`participant.ts:141`). Money truth is per-square, not per-member.
- Props: `purchasePropCard` writes only `propCards`/`entryCount` (`propBets.ts:94,98`) and no participation index at all, so Prop members are absent from `participations`, "My Entries", and any Roster.

Because the playable Entry is overloaded as the payment record, and its cardinality/shape differs per type:

- The Commissioner, seeded into `participantIds` on create, has **no Entry** until they submit picks, so they are absent from the payments roster and pot math.
- Any Member who joined but hasn't acted is invisible.
- Member-facing and commissioner-facing payment views read different shapes; "mark me paid" and "who's in the pool" cannot be answered from one place.
- Aggregate stats cannot be computed reliably — membership truth is split across `participantIds`, `entries`, `participants`, `joinedPools`, and `participations`.
- Firestore rules let ordinary members read `entries` only for themselves until the pool is `LOCKED` (`firestore.rules:191`), so a member-facing "honest pot" cannot be read from raw entries pre-lock.
- `paidStatus` is defined as commissioner-set (CONTEXT.md), and bracket play already **gates on `paidStatus==='PAID'`** (`bracketEntries.ts:227`) — so a member-writable `paidStatus` would let members self-unlock paid pools.

An earlier draft of this ADR proposed "one Entry per Member across all types." Adversarial review rejected it: it collides with Bracket/Playoff multi-entry, can't represent Squares, and would put a security-relevant field under member control. This revision adopts the reviewer's simpler alternative.

## Decision

Introduce a **Member Record** — one document per Member per Pool at `pools/{poolId}/members/{uid}` — as the single Roster and payment record for **every** Pool type. The playable **Entry** (picks/bracket/selections) is left exactly as each type models it today, including multi-Entry types.

1. **Member Record shape (deterministic ID = uid):** `{ uid, poolId, userName, role, joinedAt, paidStatus: 'PAID'|'UNPAID', paidAt?, paidBy?, memberReportedPaid?: boolean, memberReportedAt?, unitsOwned?, unitsPaid?, rebuyOwed?, rebuyPaid? }`. `unitsOwned/unitsPaid` carry Squares dues (per-square); `rebuyOwed/rebuyPaid` carry rebuy dues (e.g. Survivor), so neither `fee × members` nor a rebuy-blind sum is assumed. `userName` is populated so roster/reminder helpers that expect it (`NFLManagerView.tsx:893`, `manualReminders.ts:132`) keep working. **The rebuy transaction (`nflPools.ts:556`) writes `rebuyOwed/rebuyPaid` onto the Member Record** in the same transaction as the ledger append, so aggregates that trigger on Member Record writes never go stale.
2. **Member Record is written on join and on create.** Every join path writes the Member Record; the create path writes the owner's Member Record alongside `participantIds:[uid]`, so the Commissioner is on the Roster from t=0. Entries remain created when a Member actually plays.
3. **`participantIds[]` stays the fast membership index; Member Records are the Roster truth.** They must not drift. A single idempotent **`reconcileMembership(poolId, uid, tx)`** helper is the *only* writer of membership across `participantIds`, `participations`, `joinedPools`, and Member Records. It is **not** a naive add/remove — it **recomputes** the uid's post-write membership and units from authoritative Pool state (remaining Entries / owned squares) *inside the mutating write's own transaction*, so "delete one of many Bracket/Playoff entries" or "release some but not all squares" resolve correctly (member stays if any Entry/square remains; units decrement). **Coverage is enforced by tooling, not a hand-maintained list** (successive reviews kept finding more writers): a grep audit enumerates every current writer of `participantIds`/`participants`/`propCards`/entry ownership; each is routed through, rewritten to use, or retired in favor of `reconcileMembership`; and a test/CI guard fails the build if membership state is mutated anywhere else. Known writers to route/retire: NFL join (`nflPools.ts:138`), Bracket join (`bracketPools.ts:235`) and `createBracketEntry` arrayUnion (`bracketEntries.ts:102`), Playoff add via `submitPlayoffPicks` (`playoffPools.ts:137,213`), Squares claim/release (`squares.ts`) and auto-release (`reminders.ts:318,339`), both guest-claim paths (`participant.ts:93,157`), owner seeding on create (`poolCreation.ts:134`), Props `purchasePropCard` (`propBets.ts:94,98` — today writes no participation at all), the legacy fixers `syncParticipantIndices` (`participant.ts:225`) and `fixParticipantIds` (`poolOps.ts:532`), and all delete paths (`bracketEntries.ts:391`, `playoffPools.ts:340`). Shipped and wired **before** the backfill runs. Leaving/last-Entry-removal voids the Member Record.
4. **`paidStatus` stays authoritative and server-only, set by Commissioner (or SUPER_ADMIN).** Honor-system member self-report is a **separate** `memberReportedPaid` claim that never gates play and never sets `paidStatus`. Commissioners see claims and confirm them into `paidStatus`.
5. **One authorized `setPaidStatus` callable** mutates the Member Record and appends the payment-ledger event in a **single transaction** (today's ledger append is non-atomic and swallows failures — `paymentLedger.ts:43`). All four direct-client payment writes (`NFLManagerView.tsx:195`, `NFLManagerBentoDashboard.tsx:97`, `BracketPoolDashboard.tsx:323`, `SuperAdmin.tsx:179`) are removed in the same change.
6. **A `pools/{poolId}/rosterSummary` projection** (member count, Dues Collected, Dues Expected, paid/unpaid counts, plus a derived **guest/unclaimed-squares dues bucket** so unclaimed Squares money is not lost when the `"guest"` sentinel is skipped) is maintained server-side, **readable only by the Pool's Members, Commissioner, and admins** (not world-readable), so the member-facing pot is readable pre-lock without exposing raw entries. `rosterSummary` is **updated in the same transaction as every membership/payment mutation** (`setPaidStatus`, `reconcileMembership`, rebuy) so it never lags the Member Records it summarizes.
7. **Commissioner Aggregate Stats** are computed by a Cloud Function that triggers on Member Record writes (membership/payment) — never on Entry pick/score writes (`submitNFLPicks`/`scoreNFLWeek` rewrite entries constantly) — **plus on payout writes** (`pools/{id}/winners/*`, `poolOps.ts:504`), since Squares payouts flip there and never touch a Member Record, **and on pool-doc writes that change inclusion-predicate fields** (`status`, `closedVia`, archived) **or fee fields** (`entryFee`, `costPerSquare`, `rebuyCost`), since a Pool can cross the include/exclude boundary — or have its owed dues changed by a fee edit via `updatePoolSettings` — with no Member Record or winner write. The same trigger refreshes `rosterSummary` (Dues Expected = fee × members). (Chosen over a live inclusion query to keep the aggregate a cheap stored read.) Dues math uses **per-type adapters** for member count, dues, and payouts, and **includes rebuy dues** from `rebuyOwed/rebuyPaid` on the Member Record (written in the rebuy transaction, `nflPools.ts:556`). Payouts are sourced from the winners subcollection / payout ledger. The `playoff_entries` source bug is fixed in the same pass.
8. **A backfill migration** creates Member Records for existing Pools of all types: one per real uid in the union of `participantIds` ∪ `participants` ∪ `entries` ∪ `propCards` (Props members exist only in `propCards`) — **skipping the `"guest"` sentinel** and non-uid entries (their dues roll into the `rosterSummary` guest/unclaimed bucket) — copying `paidStatus` where an Entry already has it, never overwriting. It is a **resumable, checkpointed script** that emits post-run invariant counts (`participantId-without-member`, `member-without-participantId`, `guest-skipped`, per-type failures). New hub/summary reads are **gated on `rosterSchemaVersion`, flipped per Pool only after that Pool's own invariant checks pass** — a Pool with any failed invariant keeps the old read path until re-run, so nothing reads a half-migrated Pool.
9. **Pool inclusion is one shared predicate.** A single matrix decides which Pools count in rosters/stats/hub: exclude `COMPLETED`, `archived`, `CANCELED`, `closedVia:'ADMIN_CLOSE'`, and `sim-*` test pools. Used everywhere so aggregates never count dead or fake pools.

## Alternatives considered

- **One Entry per Member across all types (original draft).** Rejected in review: collides with Bracket/Playoff multi-entry, can't model Squares per-square money, and forces a security-relevant field (`paidStatus`) under member control.
- **Derive the Roster from `participantIds` and synthesize rows, no new doc.** No place to store per-member payment state, claims, or Squares units uniformly; self-serve claims have no target. Rejected.
- **Keep per-type membership models + a read-time adapter only.** Every consumer keeps branching forever and the drift between `participantIds` and playable records is never fixed. Rejected, but adapters *are* used inside the stats function for per-type dues/payout math.
- **New pools only, no backfill.** Leaves every existing Pool (including current test pools where the commissioner is missing) broken. Rejected — the reported bug is on existing pools.

## Consequences

- A new `members` subcollection and `rosterSummary` doc per Pool; Firestore rules grant read on both to the Pool's Members/Commissioner/admins only. Member self-writes to their own Member Record must **pin the exact diff** — only `memberReportedPaid` and `memberReportedAt` may change; `paidStatus`, `unitsPaid`, `rebuyPaid`, and every other field are denied to Members (a callable is the fallback if a rule can't express the diff safely). Each claim mutation is audited.
- `reconcileMembership` must be the sole membership writer — any path that still writes `participantIds` directly is a drift bug.
- One resumable migration touching every existing Pool; dry-run + invariant report reviewed before it runs against prod data.
- The member payments view and the commissioner mark-paid view collapse onto one Member Record shape, enabling the unified payments surface the dashboard needs.
- Squares keeps its square-level model; the Member Record only adds a per-member dues roll-up (`unitsOwned/unitsPaid`).
- If preseason timing slips, the Member Record + summary + `setPaidStatus` ship for NFL season pools first; Bracket/Playoff/Squares go behind the per-type adapters until after live testing (does not change the model, only rollout order).
